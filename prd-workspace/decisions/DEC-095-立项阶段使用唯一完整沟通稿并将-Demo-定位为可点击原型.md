## DEC-095：立项阶段使用唯一完整沟通稿并将 Demo 定位为可点击原型

- 日期：2026-08-17
- 状态：已确认
- 背景：此前把 V1.1 标记为已发布 baseline，再以 V1.2 增量和完整评审稿叠加，导致评审人需要跨多份文件拼接需求；Demo 又按生产系统模拟验证码、账号联动、并发和完整回归，增加了沟通成本、文件体积和每轮修改时间。用户明确当前仍处于立项沟通阶段，尚未进行正式产品评审。
- 决策：V1.0、V1.1、V1.2 均作为需求沟通快照，不代表已发布或已评审。客户管理在立项阶段只维护 `current/PRD_customer_management_full.md` 一份自包含主稿，按真实菜单、页面和功能组织，字段、限制、提示和正式产品失败策略写全；历史 baseline、delta、review 和旧 Demo 进入归档，仅用于追溯。产品评审通过后才建立研发评审基线。Demo 定位为类似 Axure 的可点击高保真原型：关键页面和交互可用，允许固定并预填验证码、账号独立预置数据和简化服务端机制；不要求模拟失败计数、真实并发、数据库事务、文件扫描或跨账号实时联动。Demo 验证按改动风险分级，普通调整不执行生产级全系统回归。
- 未采用方案：继续以 baseline + delta + review 作为立项阶段评审入口；把 Demo 当作可直接交付前后端的单文件生产实现；删除所有历史文档以减少文件数量。
- 原因：单一完整稿更适合逐菜单讲解和评审，历史归档仍保留决策过程；原型级 Demo 能把时间和算力集中在页面、字段、流程和角色立场，而不是模拟尚未进入研发的基础设施细节。
- 决策人：产品经理
- 影响范围：PRD_GUIDE、HANDOFF、客户管理当前 PRD、Demo 开发与验证规则、历史文件归档
