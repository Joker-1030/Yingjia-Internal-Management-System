## Quick Overview

M04 审批中心尚未完成产品评审，也未进入正式研发；本地 Working Demo 已表达当前确认范围，供产品验收和研发评审。审批中心作为独立一级菜单提供列表、详情和“发起审批”入口；平台只展示平台发起的审批及企业微信同步结果。

已确认的企业微信员工绑定和通用审批接入需求统一由本模块维护，详见第3章。员工组织和账号事实继续归M06；第一期只绑定双方已有员工、只同步平台发起的审批，具体模板另定。平台填写并发起审批，同意、驳回、撤回统一在企业微信执行，平台同步过程和结果。具体模板、同步时效及撤回/驳回后的重提方式仍以企业微信规则和后续确认结果为准。

已经确认进入审批的业务操作由各来源模块按原权限和校验准备申请，审批中保持原业务状态，企业微信审批通过后才执行原有生效规则；驳回或撤回不改变业务对象。项目取消、关键人恢复及未列入本节的操作仍按来源模块原规则直接生效。

## 1. Current Boundary

### 1.1 当前工作范围

- 独立一级菜单“审批中心”，列表、详情 Drawer、分类页签、筛选和数量入口；
- “发起审批”表单：先选择当前可发起的审批事项/企业微信模板，再按该事项动态展示并填写模板要求的字段；已映射到平台的项目、客户公司等字段使用平台下拉选项，其他字段沿用模板控件；审批人和抄送人均由企业微信模板路线预设，平台不提供选择；提交前校验申请人的企业微信绑定，提交后生成平台发起记录并进入“我发起的”；
- 审批流程编号、实例、节点、审批人、意见和进度；
- 待我处理、我已处理、我发起、抄送我的四类参与关系视图；
- 审批抄送、审批待办、审批结果通知；
- 审批回调、`已通过-业务处理失败`、回调重试和处理人失效替换的结果展示；
- 从列表进入审批详情，展示申请标题、流程编号、发起人和时间、流程进度、当前处理人、抄送人、申请内容（含申请原因）、必要业务影响及流程节点；不展示数据范围、处理位置和内部校验规则说明，标题下不重复类型及状态，流程节点不重复发起记录，完成时间仅有值时展示。关键人停用影响只展示未完成任务数及任务处理方式，不重复对象类型、客户数、关键人数或进行中审批数；同一信息只在一个区块展示；
- 详情处理人展示企业微信同步的姓名：审批中为当前节点全部处理人，已结束为实际最后处理人；无同步姓名时显示空值，不以“按模板路由”或角色名称代替。流程节点按企业微信同步的完整路线顺序全览，不仅展示当前或末尾节点，也不由平台组织推算路线；已完成为绿色、正在审批为黄色、待审批为灰色，驳回节点保留红色。每个节点分开展示节点名称与状态、处理人、实际处理时间及意见；未处理节点不伪造时间和意见，长姓名及意见换行；驳回节点使用实际驳回时间，不显示“未到达”。
- 同意、驳回、撤回仍只在企业微信执行，平台不提供直接处理按钮。

### 1.3 已确认的业务审批事项

- **审批承载**：平台表单负责校验、填写和发起；审批层级、节点、审批人和抄送人由企业微信模板维护，平台不提供选择。平台同步企业微信当前节点处理人姓名、过程和最终结果。
- **审批状态**：审批中保留原业务状态；通过后执行对应 Owner 的原业务变更；驳回或撤回可按企业微信规则修改后重新发起，原审批记录保留。
- **关键人停用**：PM、区域总监和市场副总按各自客户数据范围发起企业微信审批，`admin` 直接停用；只审批停用，恢复继续直接生效；审批通过后立即停用，并关闭未完成任务、保留历史。
- **维系任务变更**：延期、暂停、取消分别使用独立事项；具备原任务操作权限的人发起，通过后分别更新截止日期、进入暂停或取消并保留历史。
- **已开始项目中止**：仅“进行中”项目可发起；通过后才执行现有结算、框架额度、排期和待办处理；项目取消不进入审批。
- **地市责任交接**：原PM发起，一次可选1-50个本人负责地市；审批中原PM继续负责，通过后按计划日期整批生效；区域总监在主管中心内直接调整无需审批。
- **销售指标调整**：有权管理者发起，支持区域年度/季度/月度，以及PM和区域总监个人季度/月度目标的批量调整；整批通过后一次生效。

发起入口既可来自审批中心，也可来自上述业务页面的原操作按钮；业务页面提交后进入“审批中”，不直接改写业务对象。项目取消、关键人恢复等未列入事项保持现有直接生效规则。

## 2. 历史边界

已经存在的历史审批记录是不可改写的只读证据。Working Demo 中的审批样例均标记为平台发起，并按参与关系展示；历史证据不能恢复为 Current Product Rule，也不能用来扩大平台同步集合。

## 3. 企业微信员工绑定与通用审批接入（已确认专项定义，未评审、未研发）

### 3.1 目标与范围

统一在M04定义企业微信身份绑定、连接与模板接入、平台填写并发起审批、企业微信处理审批和平台结果同步。复用企业微信审批应用的模板、表单及路线；不建设平台审批引擎或模板设计器，不将自建应用“审批流程引擎”当作现有审批应用的同一能力。

第一期对接企业微信模板目录。发起人先选择有权发起的审批事项，再填写该事项定义的字段；事项字段、控件、申请人范围及模板路线由企业微信维护，平台只表达已接入事项所需的填写界面。报销、开票、付款、项目关联、关账、回款、费用确认及毛利等财务调研内容仍不因本条自动进入已确认实施范围。第1.2节来源业务仍按DEC-204直接或计划生效，不新增审批前置条件。

本章为延期模块中已确认的需求定义，不代表专项完整、评审通过或研发启动。未确认产品选择与未验证接口能力在第3.8节隔离，不能由历史讨论、Demo或接口字段补成产品规则。

### 3.2 员工核对绑定

- 由HR/人事或admin核对并维护平台已有员工与本企业企业微信已有员工的绑定。
- 一名平台员工只绑定一个本企业企业微信员工，同一个企业微信员工不可重复绑定给其他平台员工。
- 姓名只用于辅助查找；同名不能自动确认身份或自动绑定。绑定以双方稳定员工身份为准。
- 未绑定或存在绑定冲突时，禁止以该平台员工身份发起审批，提示先由有权人员处理；不改用其他员工或管理员身份代替提交。
- 本期不自动创建两边员工或账号，不覆盖部门、主管、人工角色、派生角色、账号状态，也不自动停用员工。
- 审批模块的绑定能力不等于自动打通账号或双向组织同步；企业微信扫码登录作为 P00 的独立登录方式，复用本绑定识别平台账号，具体规则见 [`P00 登录页`](./P00-login.md) →“企业微信扫码登录”和 [`DEC-261`](../../decisions/DEC-261-企业微信扫码登录.md) →“当前决定”。

内部员工、部门、主管、角色和账号的唯一产品拥有者仍是 [`M06 组织与员工`](./M06-organization.md) →“2. 用户角色”“区域总监角色的唯一来源（DEC-256）”；M04只维护跨系统绑定，不能将企业微信部门或主管信息直接转为平台角色。

### 3.3 接入与模板维护

仅admin配置企业微信连接和审批模板接入。审批事项目录、表单字段、控件、申请人范围及路线由企业在企业微信维护；平台按当前员工可发起的事项动态展示字段并提交，不提供审批人或抄送人手工指定、模板设计器、路线设计器或独立审批引擎。已映射到平台的业务字段使用平台下拉选项，其他模板字段按企业微信模板要求填写。

模板接入与员工绑定是两种维护权限：HR的绑定权限不包含连接/模板配置。模板确定前不预设所有员工都可发起任意模板；各模板的申请人范围、控件与业务校验需另行确定。能调用某个企业微信接口，也不等于取得平台中全部审批数据的读取或处理权限。

### 3.4 平台发起与同步集合

平台填写并发起审批，以绑定的真实员工身份提交至企业微信。平台只同步由本平台发起的审批，包括这些单据随后在企业微信端发生的处理和结果变化；不批量导入企业微信原生发起的历史或新审批。仅因同模板、同员工或同部门命中，不构成纳入同步集合的依据。

平台保存与企业微信原审批单的准确对应关系，展示和同步原单的真实信息；同步集合边界不能因为接口能查询更大范围而扩大。发起失败或结果未确认时不显示已成功发起；重复通知不重复创建单据或覆盖历史。

### 3.5 查看范围及企业微信处理分工

| 身份/参与关系 | 需求范围 | 不自动取得 |
| --- | --- | --- |
| 申请人 | 查看本人申请 | 其他员工审批单 |
| 审批人 | 平台查看本人参与审批的单；仅当前有权审批人在企业微信同意/驳回 | 参与过即永久具备当前审批操作权 |
| 抄送人 | 查看本人被抄送的单 | 审批或撤回权限 |
| admin | 全量核查本平台发起并同步的审批；维护连接和模板接入 | 代他人审批或撤回 |
| HR/人事 | 员工核对绑定；审批读取仍按本人参与关系 | 全量审批内容或接入配置权限 |
| 领导 | 按本人申请/审批/抄送关系查看 | 因职级、部门主管关系自动查看全部或部门审批 |

**同意、驳回、撤回统一在企业微信操作**，平台不提供这三项直接处理操作。当前有权审批人在企业微信同意/驳回；申请人仅在企业微信允许的条件下撤回。处理沿用企业微信当前权限及规则，admin不因平台配置或核查权限代审批。

平台负责填写发起审批，并在上述企业微信操作后同步真实过程和结果，不自行改审批结论。平台不开发这三项直接处理操作；本轮也不自动新增跳转企业微信的按钮或其他处理动作。

### 3.6 处理结果与跨端同步

审批查看按实际参与关系执行：当前节点审批人、申请人、抄送人及已处理人可查看对应单据，admin全量核查，不再以旧平台审批处理权限阻挡企微参与人的只读查看，也不因区域主管身份扩大到非参与单。Demo按企微已接通表达：审批中原业务保持；地市交接通过后立即或按计划生效，驳回/撤回释放重复发起限制且不变更责任；同一结果重复同步不重复迁移，生效失败保持原责任并显示既有失败状态。审批中心内不提供同意、驳回、撤回按钮。

- 平台发起及结果同步以企业微信确认的真实结果为准；失败不显示成功，不在平台单独写入一个与企业微信不一致的审批结论。
- 平台发起单在企业微信端被同意、驳回、撤回等处理后，平台同步对应单的最新过程与结果。
- 重复通知不得重复建单或覆盖历史。状态展示应反映核对后的真实企业微信结果，不能将通知到达或请求发出当作操作成功。
- 单据状态、节点状态、过程事件各有不同语义，不混作一个状态。企业微信出现通过后撤销或已支付等信息，也不自动创建平台费用冲回、回款、付款或财务记账事实。
- 同步时效、漏通知补查的产品要求及可见异常处理入口待明确；不承诺绝对实时，不新增未经确认的同步中心、业务状态、待办或通知。

### 3.7 撤回、驳回后的修改与重提

按企业微信审批规则处理。用户未选择“固定回平台修改并新单重提”，也未确认“固定在原单修改”。是否允许编辑、从何处重提、保留原编号还是生成新编号，须核对选定模板及实际客户端行为后再落具体规则。

审批中修改、撤回后编辑、驳回后重提及通过后撤销不能仅凭状态回调推导为平台可执行能力。当前不预设新旧单的自动归并规则，也不以同名、同员工、同项目猜测关联；具体方式未验证前不进入可实施验收承诺。

### 3.9 Working Demo 页面表达

- 审批中心是独立一级菜单，不归入“系统管理”；已登录用户可进入，列表数据仍按申请人、当前审批人、抄送人、已处理参与关系及admin全量核查过滤。
- 页面提供“发起审批”按钮。未绑定企业微信的系统员工点击后阻止提交并提示先完成绑定；已绑定员工先选择审批事项，页面按事项动态展示模板要求字段，平台业务字段使用下拉选项；审批人和抄送人由模板路线确定，不在发起页选择，提交后生成新的平台发起记录。
- 组织与员工页面增加“企业微信绑定”页签。HR/人事和admin可搜索系统员工、按已绑定/未绑定筛选，绑定、修改和解绑；其他角色不显示维护操作。绑定保存必须满足平台员工与企业微信员工一对一，冲突时拒绝保存。
- Demo中的企业微信员工、绑定和审批数据是可点击的工作数据，不代表已经真实联通企业微信接口；企业微信模板与审批路线仍由企业微信维护。
