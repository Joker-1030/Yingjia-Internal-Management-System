## DEC-165：员工多部门归属与停用恢复直接生效

- 日期：2026-08-24
- 状态：已确认；替代 DEC-116/159 的员工停用恢复审批与责任交接、DEC-122/142 的角色维护上限部分、DEC-130/138 的主管成员资格部分，以及 M06 单一所属部门和调岗容器规则
- 背景：Product Owner 明确要求组织与员工采用多部门成员关系和直接维护方式，并将本期员工停用/恢复收敛为 HR/admin 直接生效操作。
- 决策：
  1. 每名员工继续使用唯一稳定员工 ID 和唯一账号，但可同时属于一个或多个正常内部部门。部门关系平级，不设主部门；新增和普通编辑员工时均由 HR/人事或 admin 多选部门。部门范围展示按成员关系逐部门呈现，同一员工可在多个部门中重复出现，不创建重复员工或账号。
  2. HR/人事和 admin 可在普通员工编辑中直接调整部门集合和系统角色，保存后立即生效并记录前后值、操作人和时间；不再使用员工调岗/移动容器，不要求影响摘要、责任交接或二次确认，也不创建 M04 审批、WF 编号、待办或抄送。人工选择的系统角色仍至少 1 个、最多 5 个。
  3. 每个部门同一时点最多一名主管。主管可从任意在职非内置员工中选择；若候选人尚不是该部门成员，保存主管时自动增加其部门成员关系。解除或更换主管不自动删除既有成员关系。
  4. 区域中心主管保存时，除自动增加部门成员关系外，还必须确保员工拥有区域总监角色；角色缺失时由系统自动增加，不因人工角色数量达到 5 个而阻断，也不创建重复角色。系统记录该角色的自动来源。员工不再主管任何区域中心时，只移除由区域中心主管关系自动增加的区域总监角色；人工原有角色不删除。
  5. 本期员工停用和恢复只允许 HR/人事或 admin 操作，填写原因并确认后立即生效。二者均不进入审批，不生成 WF 编号、审批待办或抄送；停用不执行待办校验、影响阻断或责任交接。
  6. 员工停用后账号立即停用、当前会话失效，并清空其部门主管、区域/地市和客户当前责任关系；部门成员关系、系统角色、未完成任务和当前审批节点保留原员工。任务不自动关闭、清空或改派；审批不自动改派，M04 可按既有“处理人失效”规则暂停并由 admin 后续受控替换。停用员工不可登录，因此保留任务可能继续处于待处理状态。
  7. 员工恢复后账号立即启用，继续保留原部门成员关系和系统角色；已清空的主管、区域/地市或客户责任不自动恢复，未完成任务和审批仍按恢复前保留关系继续存在。本期不补造停用期间已经过去的事件任务。后续版本可另行引入停用/恢复审批，但不属于当前规则。
- Historical / Replaced：DEC-116 的“停用前完整责任交接、恢复需审批”，DEC-159 的“员工部门/角色只能通过调岗容器并需影响摘要、责任交接和二次确认，以及停用/恢复仍按主管审批”，DEC-122/142 的自动区域总监角色也受人工 1-5 上限约束，DEC-130/138 的区域中心主管必须先属于区域中心或下级部门且必须预先具备区域总监角色，以及 M06/AC/Flow 中所有相反单部门、审批式停用恢复表达。
- 未采用方案：停用时关闭或重新分配未完成任务；停用时自动改派审批；为员工设置主部门；主管只能从部门现有成员选择；系统自动角色因人工角色达到上限而阻断；恢复时自动取回已清空责任。
- 原因：保持组织维护轻量直接，同时由 Product Owner 明确接受停用员工名下任务和审批继续保留的业务结果。
- 决策人：Product Owner
- 影响范围：M03、M04、M06、M07、M08、P01、Acceptance、User Flow、Shared、Glossary、Product Boundary、客户管理 Prototype
