## DEC-093：关键人、父任务、任务执行记录与审批流程使用不可回收业务编号

- 日期：2026-08-17
- 状态：已确认
- 背景：关键人、任务主题、具体任务执行记录和审批流程目前主要以内部 ID 关联，页面缺少便于沟通、检索和审计的稳定业务编号；此前把每条执行记录都编号为独立 `MT` 任务，会混淆“一个任务包含多条执行记录”的父子关系。
- 决策：保留数据库内部稳定 UUID/ID 作为关联主键，另为正式对象生成只读业务编号。关键人使用 `KP` + 8 位公司级流水，例如 `KP00000001`；父任务使用 `MT` + 8 位公司级流水，例如 `MT00000001`；任务执行记录使用“父任务编号 + 连字符 + 父任务内 6 位子流水”，例如 `MT00000001-000001`；审批流程使用 `WF` + 8 位公司级流水，例如 `WF00000001`。父任务代表常规维系计划、某一年月生日关怀、某一节日关怀或一项公司专项；同一父任务下新生成、续期或补充的执行记录复用父任务编号，只递增该父任务内部子流水。关键人、父任务和审批流程分别使用公司级独立原子序列；每个父任务的子流水也必须通过数据库序列、行锁计数器或等价原子机制分配。所有编号不可编辑，允许断号，任务完成、取消、关闭、对象停用、审批撤回或驳回后永久保留且不回收。同一幂等键或同一执行业务唯一键重复提交返回首次对象、原父任务号和原执行编号，不再次取号。存量数据先按稳定业务键建立父任务，再按“父任务内创建时间升序、执行记录内部稳定 ID 升序”补子编号并保留映射。
- 未采用方案：把每条执行记录都分配独立 `MT` 父任务号；直接把业务编号作为数据库主键；按日期分段的 `WX/SP-YYYYMMDD-流水`；删除后回收编号；由前端或 AI 生成编号。
- 原因：父任务号用于识别计划或活动，子编号用于识别一次具体执行，两级编号能直接表达归属并支持一个任务持续生成多条执行记录；内部 ID 仍承担稳定关联，原子取号和允许断号保证并发安全。
- 决策人：产品经理
