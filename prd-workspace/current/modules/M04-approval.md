## Quick Overview

M04 是总裁、市场副总、区域总监、PM、HR/人事和系统管理员按审批关系使用的统一审批中心。用户通过“待我处理、我已处理、我发起的、抄送我的”四个页签查看同一审批实例的不同关系投影，在审批详情 Drawer 中查看业务摘要、节点时间线和处理历史，并执行当前有权的通过、驳回、撤回、转交、加签、追加抄送、代办或处理人替换。

M04 拥有审批实例、节点、流程编号、通用动作、抄送、代办、处理人失效处置、业务回调结果和审批历史；M02/M03/M05/M06/M08/M09 继续拥有各自业务对象、状态和实际生效规则。员工部门/角色编辑及停用/恢复均由 M06 的 HR/admin 直接生效，不创建 M04 审批实例、流程编号、待办或抄送；员工停用导致既有节点处理人失效时，M04 只负责暂停和受控替换。M07 只能收紧权限，P01 拥有消息已读，M10 没有审批容器。关键人调岗审批通过后若计划日未到，M04 展示来源业务的“已通过待生效”投影，审批结论仍为已通过；任职生效由 M02 拥有（DEC-164）。

## 1. 模块目标

M04 是跨业务模块的统一审批容器和审批生命周期拥有方，负责：

- 集中展示与当前用户有处理、发起或抄送关系的审批实例。
- 为每个实例生成并展示稳定流程编号，保留流程版本、路由快照和人员快照。
- 维护审批节点、应处理人、实际处理人、意见、处理时间和节点历史。
- 提供通过、驳回、撤回、转交、会签、加签、追加抄送、管理员代办和失效处理人替换等已确认的通用动作。
- 在全部审批意见完成后请求来源业务模块执行生效，并记录成功、失败和受控重试结果。
- 保留审批历史和操作日志，使发起、处理、抄送、代办、替换和回调结果可追溯。

来源业务模块继续拥有：

- 申请字段与必填规则。
- 业务影响摘要。
- 业务对象及其普通编辑。
- 业务对象状态和生命周期。
- 谁可以发起、审批路由依据及业务责任关系。
- 审批通过后的实际业务生效规则、事务边界和失败修复。

进入 M04 不会将业务对象或业务生命周期转移给审批中心。M04 也不根据通用审批能力为来源模块增加计划生效字段、业务动作或状态。

## 2. 用户角色

| 角色 | 可见与数据范围 | 可发起 | 可处理 | 代办、加签与撤回 | 自审、空范围与 403 边界 |
| --- | --- | --- | --- | --- | --- |
| 总裁 | 按审批关系及公司全局管理范围查看有权实例 | 仅从来源业务模块发起其明确允许的申请；明确无更高审批人的直接动作可形成已通过实例 | 处理路由上提节点和总裁兜底节点 | 不是普通代办人；本人是当前单人审批人时可按规则加签；本人发起且尚无处理动作时可撤回 | 不是所有申请的默认审批人；除明确直接动作外不得自审；越权实例和业务摘要不返回 |
| 市场副总 | 按审批关系及全国市场范围；部门主管待办仍按本人真实主管关系 | 从来源模块发起已定义的业务申请 | 处理实际路由给本人的省级业务责任客户任务异常、关键人变更或其他节点 | 不能普通代办；仅当前单人审批人可加签；本人发起且首个处理动作前可撤回 | 全国范围不等于可处理全部实例；系统角色不自动产生部门主管权 |
| 区域总监 | 本人主管的全部区域中心并集；未主管任何区域中心时客户审批范围为空 | 按 M02/M03/M05 的对象与责任规则发起 | 处理所属地市交接、市级/区县级业务责任客户任务异常、关键人任职变更及本人真实主管待办 | 不能普通代办；仅当前单人审批人可加签；本人发起且首个处理动作前可撤回 | 不使用单一“本区域”扩大范围；本人申请按规则上提，不得自审 |
| PM | 当前有效负责地市；无有效负责地市时客户审批范围为空 | 从 M02/M03/M05/M08 的有权业务对象入口发起 | 仅处理明确的接收节点或本人同时作为合法部门主管的待办 | 不能普通代办；仅当前单人审批人可加签；本人发起且首个处理动作前可撤回 | PM 角色本身不产生普通审批权；超范围流程、数量、候选和对象名称不返回 |
| HR/人事 | 本人在其他既有流程中为发起人、应处理人、实际处理人或抄送人时可见 | 不从 M06 发起员工部门/角色编辑或停用/恢复审批 | 仅处理其他来源模块已明确定义且本人合法参与的审批 | 不能代办客户审批；M06 直接员工操作不进入本模块 | 没有客户业务审批范围；直接请求客户停用或任务异常审批返回 403 且不泄露客户信息 |
| 系统管理员 | 公司全局查看与处理 | 可从来源模块执行已有全局操作，但正常申请仍保留业务路由 | 可按真实 admin 身份处理本人节点或受控代办非本人节点；可按规则替换失效处理人 | 代办原因 5-500 字必填；保留原应处理人与实际 admin；仅当前单人审批人按规则加签；本人发起撤回仍受时机限制 | 不伪装业务角色、不改写业务责任快照、不绕过正常路由；全局权限不等于创建未定义审批 |

### 2.1 通用角色规则

- 发起资格由来源业务模块定义，M04 不从角色名称推导新的发起入口。
- 处理资格必须同时满足当前节点关系、提交时路由快照、人员有效性、对象范围和最终权限。
- 除来源明确为直接生效并生成已通过实例的动作外，发起人不得作为同一实例的后续审批人；路由相同时逐级取有效业务上级，仍无人时由总裁兜底。
- 抄送只提供审批所需的脱敏快照和结果知会，不产生审批权或父业务对象权限。
- 无权入口隐藏；直接地址、列表、计数、搜索、候选、详情、附件和受控进入均重新鉴权。越权返回 403，不返回对象是否存在、名称、数量、状态或缓存内容。

### 2.2 M07 只能收紧

M07 的菜单/页面、操作、字段和附件权限只能进一步收紧 M04 已确认的业务上限，不能：

- 扩大业务审批资格或对象数据范围。
- 改变既有审批路由或禁止自审规则。
- 赋予 HR/人事客户业务审批权限。
- 让普通角色获得管理员代办或失效处理人替换能力。
- 让抄送人获得审批权或父业务对象权限。
- 放宽来源业务模块已经确定的敏感字段上限。

## 3. 核心对象

### 3.1 M04 拥有的对象与关系

| 对象/关系 | 产品含义 | 所有权与关系 | 可编辑性 |
| --- | --- | --- | --- |
| 审批实例 | 一次正式审批申请的统一容器，关联业务类型、业务快照、节点、关系和结果 | M04 拥有；关联来源业务对象但不拥有该对象 | 仅通过合法审批动作变化，不允许普通编辑 |
| 审批节点 | 实际流程中的接收、单人审批、预设会签或动态加签节点 | M04 拥有；人员计算依据来自来源业务、M06、M07、M08 | 只能由当前合法动作推进 |
| 流程编号 | 用户识别和沟通审批实例的永久编号 | M04 拥有，与内部稳定实例 ID 一一关联 | 只读，不修改、不回收 |
| 发起人与提交身份 | 谁以哪一个有效业务身份提交申请的快照 | M04 保存提交快照；发起资格由来源模块拥有 | 只读，提交后不改写 |
| 应处理人与实际处理人 | 路由计算出的责任人和真实执行动作的人 | M04 保存节点关系和处理历史；人员事实来自 M06/M08/M07 | 只读；转交、代办或替换以新增历史表达 |
| 管理员代办记录 | admin 以真实身份处理非本人待办的记录 | M04 拥有，关联原应处理人、实际 admin、原因和时间 | 只追加，不覆盖原关系 |
| 审批意见与处理动作 | 通过、驳回、撤回、转交、会签、加签、追加抄送、代办和替换 | M04 拥有通用动作与审计；业务影响由来源模块执行 | 处理后不可改写 |
| 抄送关系 | 提交时或审批中建立的只读知会关系 | M04 拥有关系；P01 拥有消息展示和已读状态 | 默认关系唯一；追加时去重 |
| 处理人失效事实 | 当前处理人因人员、账号、资格或范围变化不能继续处理的节点异常 | M04 拥有暂停、异常、替换和告警历史；失效事实来自外部资格源 | 只通过受控替换恢复，不作为普通编辑 |
| 业务回调结果 | 审批意见完成后，来源业务执行生效的结果和重试历史 | M04 拥有结果表达；来源业务模块拥有实际写入和修复 | 只追加结果与重试记录 |
| 审批历史/操作日志 | 发起、节点、意见、转交、加签、抄送、代办、替换、回调和重试的时间线 | M04 拥有；来源业务历史仍在对应模块 | 长期保留，只追加不改写 |
| 受控跳转 | 从 M01、P01 或来源业务模块进入有权审批详情的上下文 | M04 拥有审批详情鉴权；进入后不扩大父对象权限 | 每次进入重新鉴权 |

### 3.2 四个页签只是列表投影

“待我处理”“我已处理”“我发起的”“抄送我的”是同一审批实例按用户关系形成的四种列表投影，不是四类审批对象，也不分别保存第二份状态。

- 待我处理：当前节点责任人为本人、本人属于当前会签节点，或本人是可受控代办的 admin。
- 我已处理：本人曾作为实际处理人完成节点动作。
- 我发起的：本人提交的审批实例。
- 抄送我的：本人拥有抄送关系的审批实例；已读或流程结束不使关系移出。

发起事件和抄送关系不是审批节点；流程结束后仍保留最后真实业务节点名称，不增加“已结束”伪节点。

### 3.3 不属于 M04 的业务对象

| 业务对象 | 所有者 | M04 的使用边界 |
| --- | --- | --- |
| 客户、关键人、任职 | M02/M09 | 只保存审批所需快照和关联，不维护客户或任职 |
| 任务、专项、KPI、维系记录 | M03 | 只承载异常/补录审批，不改变任务生命周期 |
| 停用对象、停用/恢复记录和影响 | M05 及对象所有者 | 只承载审批实例，不建立停用生命周期 |
| 员工、内部部门、账号和角色关联 | M06 | 只消费人员与主管资格，不维护组织员工 |
| 区域、省份和地市责任 | M08 | 只消费路由和迁移结果，不修改责任关系 |
| 行业、集团、客户公司、客户部门、标准岗位 | M09 | 只读展示业务快照，不维护主数据 |
| 导入批次 | M10 | 没有审批发起关系，不创建或改写批次 |
| 消息与消息已读 | P01 | M04 只输出通知事件，不维护已读状态 |

## 4. 页面与入口

### 4.1 审批中心入口

六类角色按其审批关系、业务数据范围和 M07 最终收紧结果进入审批中心。无权入口不显示；直接访问时重新鉴权。系统管理员通过筛选中的“公司全局”范围查看全部有权实例，不新增第五个页签。

### 4.2 四个固定页签

| 页签 | 收录范围 | 主要内容和操作 |
| --- | --- | --- |
| 待我处理 | 当前节点责任人为本人、本人为当前会签成员，或 admin 可受控代办 | 查看当前节点；按权限执行通过、驳回、转交、加签、追加抄送或代办 |
| 我已处理 | 本人作为实际处理人处理过的节点 | 查看本人意见、处理时间和后续结果 |
| 我发起的 | 本人提交的实例 | 查看进度；审批中追加抄送；首个处理动作前撤回 |
| 抄送我的 | 提交时或运行中建立给本人的抄送关系 | 只读查看脱敏快照和结果；不能审批或获得父对象权限 |

`Clarification`：本模块沿用旧 F011 和当前 Candidate 的标准页签名“待我处理 / 我已处理 / 我发起的 / 抄送我的”。“我的待办 / 已处理”是否作为正式替代名称仍待治理，本次不改名。

### 4.3 审批列表

列表列包括：

- 流程编号
- 业务类型
- 业务对象摘要
- 申请人
- 发起时间
- 当前节点
- 当前处理人
- 审批实例状态
- 完成时间
- 更新时间
- 当前有权操作

同一审批实例在列表和详情中使用同一流程编号、当前环节、节点顺序、处理人和状态事实。页签数量从同一授权结果集计算；同一实例不得在同一页签重复计数。

### 4.4 筛选、分页与排序

筛选项：

- 流程编号
- 业务类型
- 申请人
- 当前处理人
- 审批实例状态
- 发起开始日期
- 发起结束日期
- 完成开始日期
- 完成结束日期
- 业务对象名称：最多 100 字；与流程编号分别筛选

普通列表默认每页 20 条，可切换 20/50/100。默认按发起时间倒序，同一时间按稳定实例顺序倒序。重置恢复当前角色有权范围的全部实例，不扩大权限。

### 4.5 审批详情 Drawer

审批详情使用右侧 Drawer，固定包含：

1. 顶部业务摘要：展示来源业务模块提供的最小必要只读快照和影响摘要。
2. 中部节点时间线：展示真实节点名称、应处理人、实际处理人、动作、处理时间和意见。
3. 底部处理与流转记录：展示发起、抄送、转交、会签、加签、代办、替换、业务回调和重试历史。
4. 当前动作区：只展示当前用户、当前节点和当前实例状态下合法的动作。

业务摘要只是来源业务快照的只读投影，不创建第二套客户、关键人、任务、停用、员工、区域或主数据对象。关键人手机号在审批快照中对全部角色统一脱敏；抄送、处理、代办或 admin 身份均不产生明文上限。

### 4.6 节点时间线

- 已通过节点显示绿色。
- 当前待处理节点显示黄色。
- 未到节点显示灰色。
- 拒绝或驳回的终止节点显示红色。
- 会签和加签展开后按成员分别展示结果、时间和意见。
- 列表流程进度与详情时间线使用同一节点事实。
- 流程结束后保留最后实际环节名称，不显示“已结束”伪节点。

### 4.7 当前动作与确认容器

通过、驳回、撤回、转交、加签、追加抄送、替换处理人和管理员代办均使用对应的确认容器，显示本次动作、必填输入、影响对象和提交状态。会签是预设节点成员各自处理，不提供运行中编辑成员的入口。

### 4.8 业务失败反馈

审批意见全部通过但来源业务生效失败时，详情展示“已通过-业务处理失败”、失败时间、请求标识、自动重试进度和历史。持续失败后向 admin 展示受控重试入口；通过按钮不再出现，也不提供通用“关闭”按钮。

### 4.9 受控进入与跳转边界

- M01 工作台、P01 消息和来源业务模块可将用户带入对应审批详情。
- 每次进入、返回和打开附件均重新鉴权；中途失权后不展示缓存快照。
- `Clarification`：当前资料没有定义从审批详情统一反向跳转到父业务对象的按钮、目标和角色上限。本 Candidate 不新增通用反向业务跳转。

### 4.10 页面反馈

页面完整支持 Loading、Empty、Empty Result、Error、PermissionDenied、Submitting 和 Success，具体分层见第 7 章。

## 5. 用户操作

| 操作 | 谁可以执行 | 前置与确认 | 成功结果 | 失败保护与反馈 |
| --- | --- | --- | --- | --- |
| 查看 | 对该实例有处理、发起、抄送、管理或审计关系的角色 | 每次打开列表、详情和附件重新鉴权 | 展示有权字段、节点和历史 | 无权返回 403，不泄露实例或业务对象信息 |
| 搜索/筛选/分页 | 有审批中心查看权的角色 | 条件始终受当前关系和数据范围约束 | 更新同一授权结果集，不改变实例 | 加载失败保留条件并提供重试 |
| 通过 | 当前合法节点处理人；admin 可按代办规则处理 | 意见 0-500 字；提交前重校对象、责任、目标、权限和当前节点 | 进入下一节点；无下一节点时请求来源业务生效 | 重复提交只保留一个结果；旧快照或资格变化时阻止并提示刷新 |
| 驳回 | 当前合法节点处理人；admin 可代办 | 原因 5-500 字必填 | 实例结束为已驳回；来源业务保持申请前状态 | 提交失败不改变节点或业务对象 |
| 撤回 | 发起人本人 | 尚无接收、审批、会签或加签人员执行任何处理动作；原因 5-500 字 | 实例结束为已撤回，不执行业务回调 | 首个处理动作后入口消失；非法请求提示状态冲突，不改变流程 |
| 转交 | 当前节点处理人 | 目标员工符合节点角色、组织链和对象范围；原因 5-500 字 | 当前节点转给合法目标，原应处理人和转交链保留 | 非候选不出现；伪造请求 403；不能绕过责任链 |
| 会签 | 流程定义中的 2-10 名预设成员 | 每名成员分别提交意见；运行中不能增删成员 | 全员通过后进入下一节点；任一驳回则实例结束为已驳回 | 保留全部成员各自状态、时间和意见 |
| 加签 | 当前单人审批人 | 选择 1-5 名合法人员；原因 5-500 字；不得重复选择现处理人或已有成员 | 全部加签人通过后回到原审批人继续处理 | 任一加签人驳回则实例立即驳回，不回原节点 |
| 追加抄送 | 审批中的发起人或当前处理人 | 选择 1-20 名员工；说明 0-500 字；自动去重 | 立即建立抄送关系并发送通知，后续接收结果 | 不改变审批状态和处理人，不授予父业务对象权限 |
| 管理员代办 | 仅 admin | 处理非本人待办时填写 5-500 字代办原因 | 保存原应处理人、实际 admin、原因和时间 | 不伪装业务角色，不改写责任快照；提交失败不改变节点 |
| 替换失效处理人 | 动态加签人由原审批人选择；单人节点和预设会签由 admin 受控选择 | 新人员符合原节点角色、组织链和数据范围；原因 5-500 字 | 保留前后人员、资格依据、既有意见和替换时间，流程恢复处理 | 无合法候选时继续暂停并告警，不自动通过或驳回 |
| 业务回调/受控重试 | M04 请求来源模块执行；持续失败后仅 admin 使用受控重试 | 审批意见已完成；每次重试使用同一业务结果关系 | 业务成功只生效一次，记录实际成功时间 | 失败保持原业务状态；最多自动重试 5 次；不重复审批、不新增通用关闭 |

`Clarification / Governance Needed`：AC-F011-09 使用“当前处理人执行撤回”的表述，而 DEC-098 和当前正文明确由发起人本人在首个处理动作前撤回。本 Candidate 保留 AC 原文及该差异，不把当前处理人扩展为新的撤回主体。

### 6.4 抄送与通知规则

- 提交成功时立即建立默认抄送关系并发送发起通知。
- 审批通过、驳回、撤回或进入业务处理失败时，复用同一关系发送结果通知，不重复创建关系或计数。
- 审批中追加抄送从追加成功时生效，并接收后续结果通知。
- 发起和抄送作为独立事件展示，不冒充审批节点。
- 消息是否已读、消息列表和消息跳转生命周期由 P01 拥有。

### 6.5 一致性与历史规则

- 同一业务正式提交只产生一个审批实例和一个流程编号；相同提交重复发生时返回原结果。
- 同一节点的重复点击或网络重试只产生一个有效动作。
- 处理动作前重新检查业务对象、当前责任、目标有效性、处理资格和业务版本；事实变化时不允许基于旧快照继续。
- 审批通过后的业务生效只允许成功一次；失败重试不产生第二个业务结果。
- 流程编号、节点、意见、人员、抄送、代办、替换、回调和重试历史长期保留，只追加不改写。
- M04 继承来源业务对象已有附件权限和保留规则，不复制附件为审批中心自有对象。

## 7. 状态与反馈

### 7.1 页面状态

| 页面状态 | 用户看到什么 | 可执行行为 |
| --- | --- | --- |
| Loading | 页面或详情正在加载 | 等待；超过正常时间后进入 Error 并可重试 |
| Empty | 当前有权范围没有审批关系数据 | 保留页签和可用筛选，不显示伪造数据 |
| Empty Result | 当前筛选没有匹配结果 | 保留条件，可重置 |
| Error | 加载失败或超时，显示明确原因和重试 | 保留当前页签和筛选，不将错误当业务状态 |
| PermissionDenied | 无权访问或中途失权 | 显示 403，不泄露对象；清除失权缓存 |
| Submitting | 审批动作正在提交 | 按钮禁用，避免重复动作 |
| Success | 当前查看或动作成功 | 刷新同一实例、页签数量和节点结果 |

### 7.2 审批实例状态

当前已确认的通用审批实例状态集合：

| 状态 | 含义 |
| --- | --- |
| 审批中 | 实例仍有待接收、待审批、待会签或待加签节点 |
| 已通过 | 审批意见已完成，且没有未完成的业务处理失败 |
| 已驳回 | 合法节点驳回，审批结束，来源业务保持申请前状态 |
| 已撤回 | 发起人在首个处理动作前撤回，审批结束且不执行业务回调 |
| 已通过-业务处理失败 | 审批意见已经通过，但来源业务生效失败；审批结论保留，原业务状态保持；同一对象的停用/恢复在受控重试成功前不得重新发起 |

### 7.3 节点状态与颜色

- 已通过：绿色。
- 当前待处理：黄色。
- 未到达：灰色。
- 拒绝或驳回：红色。

会签和加签成员分别保存和展示状态、时间和意见。节点展示状态不扩充审批实例状态枚举。

### 7.4 处理人失效

处理人失效表达为：

- 当前节点异常；
- 流程暂停；
- 向 admin 告警；不为普通业务角色生成审批待办或失败提醒；
- 按原角色、组织链和数据范围受控替换；
- 无合法候选时继续暂停；
- 不自动通过、驳回或静默重算人员；
- 业务对象保持审批前状态。

`Clarification / Governance Needed`：处理人失效目前不定义为新的审批实例终态。它属于节点异常、流程暂停还是另一个通用状态层次仍待正式治理。

### 7.5 已通过待生效

`Current Rule（DEC-164）`：“已通过待生效”是来源业务在审批结论已通过、计划生效时刻尚未到达时的关联展示，不是新的 M04 通用审批实例状态。对关键人调岗，实际生效取审批通过时刻与计划调岗日 00:00 的较晚值；等待期间原任职继续有效。

M04 只展示该来源业务投影，不为没有计划生效字段的业务新增该状态，也不把审批结论从“已通过”改写为其他结论。

### 7.6 业务对象状态

| 来源模块 | 它拥有的业务状态示例 | M04 边界 |
| --- | --- | --- |
| M02 | 关键人、任职及调岗生效结果 | 只展示关联审批结果，不定义任职状态 |
| M03 | 任务、补录、专项和执行记录状态 | 不以审批状态替代任务状态 |
| M05 | 停用/恢复记录及关联展示 | 不建立第二套停用状态机 |
| M06 | 员工、账号和员工停用/恢复业务状态 | 不改变员工状态枚举 |
| M08 | 地市责任和交接业务状态 | 不修改负责人关系 |
| M09 | 客户主数据业务状态 | 不维护主数据状态 |

审批中、已通过或已通过待生效不自动表示业务对象已经改变。实际业务状态只在来源业务生效成功后变化。

### 7.7 错误与失败保护

| 场景 | 用户反馈与保护 |
| --- | --- |
| 审批提交失败 | 保留申请或动作输入；不创建重复实例、编号或节点结果 |
| 重复提交 | 返回首次有效结果，不生成第二实例或第二动作 |
| 并发/版本冲突 | 告知当前信息已被其他人处理或修改，展示最新摘要并要求刷新；不覆盖现有结果 |
| 业务对象变化 | 处理前重新校验；申请已不适用时阻止基于旧快照继续 |
| 目标对象失效 | 当前动作不能通过，提示目标已失效并要求来源模块处理 |
| 权限或责任变化 | 失去资格的用户不能继续处理；按处理人失效或 403 规则反馈 |
| 处理人失效 | 流程暂停、节点标记异常、受控替换并告警；无候选时持续暂停 |
| 业务回调失败 | 审批结论保留，原业务状态保持，进入“已通过-业务处理失败”；同一对象的停用/恢复锁定重复发起 |
| 无权限 | 入口隐藏；直接请求返回 403，不泄露流程和业务对象 |

业务回调失败后按 1、5、15、30、60 分钟最多自动重试 5 次，每次只允许产生一个业务结果。持续失败时通知 admin，并提供按请求标识的受控重试入口。受控重试不重复审批，不提供通用“关闭”按钮；每次结果和历史均保留。客户对象停用或恢复进入该状态后，原对象分别保持正常或已停用；受控重试成功前，同一对象不得重新发起停用或恢复，也不得创建第二审批实例。

### 8.1 当前通用审批引用顺序

来源业务模块完成申请字段、影响摘要、对象状态和发起资格校验后，向 M04 建立审批实例。M04 固化流程版本、路由和人员快照，按实际节点处理；驳回或撤回时来源业务保持原状态，全部审批意见通过后由来源模块执行实际生效。业务生效失败时，M04 保留审批结论和失败历史并受控重试，来源业务保持生效前状态。

这段产品说明不创建新的 User Flow 文件，也不替代上述机械迁移 Flow。

## 9. 权限边界

### 9.1 M04 拥有

- 审批实例、节点、流程编号和流程版本快照。
- 应处理人、实际处理人、意见、动作、抄送、代办和替换历史。
- 四页签关系投影、节点时间线、审批详情和操作日志。
- 处理人失效的暂停、告警和受控替换。
- 业务回调结果、自动重试结果和 admin 受控重试入口。
- 审批详情的对象级鉴权和最小必要脱敏快照。

### 9.2 来源模块拥有

- 谁可以发起哪一种审批。
- 申请表单、字段、影响摘要和业务对象版本。
- 业务对象和业务对象状态。
- 审批路由所依赖的客户、任务、员工、区域或主数据责任。
- 审批通过后的业务生效规则、实际生效时间和失败修复。

### 9.3 管理员、主管与自审边界

- admin 可以公司全局查看和处理，但正常申请仍按来源业务路由。
- admin 处理非本人节点时属于代办，必须保留真实身份、原应处理人和 5-500 字原因。
- 部门主管审批资格来自 M06 的真实主管关系，不由市场副总、区域总监、PM 或 HR 系统角色天然授予。
- 发起人不得自审；路由命中本人时逐级上溯，仍无人时由总裁兜底。只有来源明确的直接动作可以形成已通过实例并保留完整审计。
- 转交和失效替换都不能自由选择无关人员，必须保留原节点业务资格。

### 9.4 直接访问、抄送和跳转

- 列表、数量、搜索、候选、详情、附件、抄送快照和进入上下文使用同一权限结果。
- 抄送不产生审批权或父业务对象权限。
- 失权后不继续展示缓存内容。
- 当前没有通用反向业务跳转能力；不得由权限模板或页面实现自行补造。
